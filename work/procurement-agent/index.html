Overview

  • An events business ran purchasing through a shared Gmail inbox, with every quote, invoice and bank-detail change checked by hand.
  • Built an agent that extracts documents with Claude, validates them deterministically and prepares POs and bills for human approval.
  • 1,032 backend tests; the ingestion worker has no send credentials, and an import-graph test pins which modules can send.

Problem

An events business ran purchasing through a shared Gmail inbox. Vendors sent quotations, tax invoices, credit notes and payment reminders as PDFs and office files, mixed in with inquiries and marketing mail. Staff read each one by hand, checked GST details, raised POs, matched invoices and watched for changed bank accounts. Every step could go wrong: a duplicate payable, an acknowledgment to the wrong party, or a new bank account nobody noticed.

Solution

A worker on a systemd timer reads the inbox over IMAP and sends attachments to Claude on Bedrock as native PDF document blocks. Returned fields go through deterministic validation, three-key deduplication and a policy table, which create vendors, estimates, purchase orders with deterministic PDFs, and pending bills. A FastAPI and React app shows each thread as a purchasing conversation with an action inbox. The agent only prepares; people send POs, approve invoices, change bank details and record payments.

Architecture

  1. A systemd timer runs a worker pass every 5 minutes; IMAP fetches unseen messages oldest-first within a date bound.
  2. Attachments are hashed, stored content-addressed and sent to Claude on Bedrock as native PDF document blocks.
  3. A forced tool call returns schema-validated fields; deterministic GSTIN, ledger and three-key dedup checks follow.
  4. A policy table decides the disposition; complete estimates get an idempotent PO record and a deterministic PDF.
  5. The worker only enqueues acknowledgments; a separate outbound drain sends them behind three fail-closed gates.
  6. A person sends the PO in-thread; the returning invoice auto-matches and lands as a pending bill.

Key decisions

The ingestion worker cannot send, by design

The worker's environment holds no SMTP credential, every unit refuses to start if a stray .env exists, and a test walks the import graph to pin which modules may transmit. Automatic acknowledgments run in a separate drain behind three gates (environment pause, persisted admin pause, category allowlist), re-checked at send time. Sending POs, approving invoices, changing bank details and recording payments are human-only, enforced by tests.

The model classifies; code decides what happens

The extractor reports what a document is and a deterministic policy module decides what happens to it, which stops an invoice-shaped purchase order from being acknowledged as a payable. Mail classification reuses the single extraction pass, so two models can never disagree about the same message, and anything ambiguous goes to a person instead of creating a record.

Document text is data, never instructions

PDFs go to the Bedrock Converse API as native document blocks at temperature 0 with a forced tool call, so output is always validated JSON. The system prompt treats any instruction inside a document as data, and a prompt-injection invoice is a permanent regression fixture. Throttling parks a message as retryable; a truncated tool call is rejected, never half-parsed.

Idempotent at every layer, with tested restores

Three dedup keys catch three different repeats: the Gmail message ID, the attachment's SHA-256 and a business composite key for a resent invoice. PO preparation is idempotent. SQLite online backups with a SHA-256 manifest go to S3 every 6 hours, and a daily timer restores the latest one into an isolated directory and verifies it.
